# Career Quest UX review

Reviewed 2026-09-23 at http://127.0.0.1:3002. The app supports inspecting development data and authoring a personal plan, but the required recommendation → activity completion → visible progress loop could not be completed.

## Method and scope

Expert walkthrough, not a usability study with participants. Inspected the live Russian interface, its accessibility tree and a screenshot at the browser's existing narrow viewport. Walked through employee E0001, employee E0137 without an imported goal, activity filters, HR overview, HR employee detail and import empty-input validation. Read implementation sources to distinguish missing controls from undiscovered controls.

Requirements baseline: Career Quest sections 3–9 of the source DOCX in `case_source/`; the dataset README; `docs/prototype-product-direction.md`; and `docs/quarterly-review-requirements.md`. The latter two extend the original case. `docs/implementation-status.md` identifies planned work but is not fully synchronized with the running app: it says no live AI calls, while the UI exposes an OpenAI assistant. The checkout contains pre-existing uncommitted work; this is a snapshot review, not a release certification.

Two assistant starter requests were made against synthetic profiles and retained as assistant history. No valid plan changes, imports, resets or activity completions were committed. An invalid draft was rejected and discarded by reload. No application code was changed.

## Findings

Severity: P1 prevents a required journey or materially misleads a decision; P2 creates avoidable confusion, effort or recovery risk.

### UX-01 · P1 · No activity-completion path

**Reproduce:** enter E0001 → Activities → Available. Five activities remain. System Design Basics (`EV_005`) says “Доступно для участия,” but its card has no start, add-to-plan or complete control. The card implementation renders information only (`components/career/activity-card.tsx`).

**Impact:** the case's central learning feedback loop cannot be demonstrated. Editing a personal milestone to “reached” cannot substitute: the UI correctly says this is a self-report and does not update assessed skills.

**Change:** connect an eligible activity to the plan and a clearly labeled demo completion action. Show the actual effective-skill before/after values and the unchanged assessment/module state where reassessment is required. Repeated submission must not grant another gain.

**Acceptance:** E0001 completes EV_005 once; API Design effective level changes 2 → 3 and System Design 1 → 2 under the supplied gain/cap rules; assessment baselines remain unchanged. A second submission changes neither value. Show these effects next to the completion confirmation, then refresh affected suggestions.

### UX-02 · P1 · The tested AI entry point fails; recovery requires rewriting the request

**Reproduce:** E0001 → “Помоги начать.” Exact UI output: “Сервис ИИ не смог выполнить запрос.” The result states “Подтверждённая активность не выбрана.” It reports `rules · 0.5 s`. E0137 produced the same failure, `rules · 0.2 s`, plus a useful missing-goal question.

**Impact:** an honest fallback prevents fabricated advice, but does not fulfill the required 1–3 recommendations. The starter button disappears after the failure; the input is blank and Send disabled. The text says to retry, but this returned fallback has no dedicated retry action. The source shows Retry only for a separate request-error state (`components/career/assistant-panel.tsx`).

**Change:** fix provider availability separately from UX recovery. Retain a “Retry this request” action on provider-failure results, preserving the original prompt. Keep editing and evidence available. Any rule-based alternative must be labeled and grounded.

**Acceptance:** a successful request returns 1–3 valid activities with traceable grade/target, gap and participation factors within the total deadline; a failure retains a one-click retry and useful non-AI navigation. Provider root cause was not diagnosed in this review.

### UX-03 · P1 · Career goals and activity eligibility use different contexts

**Evidence:** the plan offers all role/grade targets. Activities explicitly say availability uses current role/grade. `lib/career/eligibility.ts` checks only `employee.role` and `employee.grade`; the learning page does not use the focused plan target.

**Concrete example:** E0001 has a Middle Backend Engineer goal. Cloud Certification Prep (`EV_009`) has no prerequisites, but is excluded as outside the current role/grade. Target-context eligibility is never evaluated. The later product direction explicitly permits the complete current OR target role/grade pair, subject to other constraints.

**Impact:** changing direction updates the destination but not the route available to reach it.

**Change:** apply the versioned transition policy consistently in catalog and recommendation eligibility. Explain “Available through your chosen target” and show the catalog audience. Preserve current employment and all prerequisite/history checks. This is a gap against the later direction, not an assertion that the original case required target-context access.

### UX-04 · P1 · HR cannot distinguish people who need different interventions

**Observed:** HR shows “Не сформированы: 200 сотрудников. Персональные рекомендации пока недоступны.” `app/hr/dashboard/page.tsx` derives that count from all employees, not recommendation records. The table has employee, role/grade and target, but no recommendation status.

**Impact:** HR cannot distinguish no goal, provider failure, no eligible route, never requested, stale advice or a valid next step. The hard-coded statement will remain misleading as assistant recommendations become usable.

**Change:** derive status from current decision records; expose filters and a per-person reason/action. Count statuses separately. Preserve the current non-ranking presentation.

### UX-05 · P2 · Missing target looks like zero critical gaps and no visible skills

**Reproduce:** select E0137. Target and coverage correctly show no goal/“—”, but the adjacent card says “Критичные дефициты: 0” and instructs the user to prioritize target requirements. Skills default to “Требуется 0”; existing evidence is hidden until “Все навыки 60” is selected.

**Impact:** “not evaluated” is easily read as “nothing missing.” Goal discovery begins with an empty skills area despite available evidence.

**Change:** default to known skills when no mapped goal exists. Replace the critical-gap count with “Choose a target to compare requirements.” Keep arbitrary goals valid and offer one prominent goal-definition action.

### UX-06 · P2 · Plan editing lacks draft protection and complete goal lifecycle controls

**Reproduce:** E0137 → Add goal → enter a draft → Add milestone → Save with blank outcome/criterion. A useful localized error appears: “Перед сохранением заполните цель, результат и критерий успеха.” Reload removes the draft without a warning. The inspected editor has no draft persistence or dirty-state protection. It also offers Add goal but no remove/archive/cancel-new-goal action.

**Impact:** accidental refresh/navigation loses work; an accidental blank extra goal is awkward to recover from. Focus selection can look immediately applied while the rest of the dashboard still represents the saved plan.

**Change:** show unsaved state, preserve drafts or warn before leaving, provide Cancel and archive/remove goal controls, and label when focus changes take effect. Identify invalid fields inline, preserving the existing summary error.

### UX-07 · P2 · Catalog emphasizes inventory over the next useful action

**Observed:** default All Activities begins with four mandatory items, including already-completed compliance training. The assistant defaults to EV_001 even after selecting the Available filter. All 40 activities remain in its selector. Cards expose generic `+1` and caps but not this employee's expected before/after result or target contribution.

**Impact:** users must reconcile the filter, a disconnected activity selector and eligibility labels before deciding what matters. Available does not necessarily mean useful for the focused goal.

**Change:** default to relevant available development activities; retain All and Mandatory views. Put “Discuss this activity” on each card to carry context into the assistant. Show “API Design 2 → 3; closes the effective gap; assessment still required” instead of requiring mental arithmetic. Display zero personal gain explicitly when at/above the cap.

### UX-08 · P2 · Evidence is technically traceable but difficult to read as an employee

**Evidence:** the assistant renders evidence IDs inline and expanded evidence as `JSON.stringify(...)`, with model/rules, latency and short decision ID always visible. This is confirmed in `components/career/assistant-panel.tsx`; successful recommendation prose remains untested.

**Impact:** a user must interpret machine fields to verify a consequential explanation. This falls short of the design's progressive, ordinary-language explanation requirement.

**Change:** show a human summary first: goal used; relevant assessed/effective level; requirement; applicable participation fact; expected gain and limitation. Keep raw JSON and technical IDs in a secondary diagnostic disclosure. Link skill changes to the specific dated source activity or assessment.

### UX-09 · P2 · HR collaboration and visibility disclosure are incomplete

**Observed:** HR can inspect the employee's plan but cannot add an attributed suggestion. Its assistant is a separate HR conversation; E0001's just-created employee fallback conversation was not visible there. No plan-change timeline or employee-facing explanation of HR access appeared in the inspected dashboard. The provider-disclosure text explains OpenAI transmission, which addresses a different visibility question.

**Change:** expose authorized employee conversation/evidence history and attributed plan changes; add HR proposals with accept/edit/dismiss controls for the employee. State who can view development records next to the plan/conversation entry point. These are later-spec scope gaps; do not silently grant HR ownership of the employee's plan.

## What works well

- Imported goals are immediately usable; missing goals do not silently become next-grade ambitions.
- Assessment baselines, course-derived effective levels and formal module closure are distinguished. The 2/15 count for E0001 is explicitly not a promotion guarantee.
- Critical requirements are visible and separated from other requirements.
- Mandatory learning is labeled and excluded from voluntary eligibility.
- The assistant failure is explicit and does not invent a recommendation; missing-goal fallback retains a useful question.
- HR gap denominators explain the target comparison; employees appear in source order without a performance leaderboard.
- Import explains merge/conflict behavior before submission and handles an empty selection clearly.
- The narrow layout stacks cleanly in the inspected screenshot; navigation collapses into a menu. This is not a full responsive/accessibility certification.
